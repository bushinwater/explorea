# .NET Project Info

> Dokumentacija za rad sa .NET backend delom projekta.  
> Ovaj fajl opisuje inicijalizaciju projekta, organizaciju foldera i fajlova, kao i način pokretanja i povezivanja komponenti projekta.  

---

## 1. Svrha backend projekta

Backend deo sistema je zadužen za:

- obradu poslovne logike,
- komunikaciju sa bazom podataka,
- izlaganje API endpoint-a koje koriste frontend i drugi klijenti,
- validaciju ulaznih podataka,
- autentifikaciju i autorizaciju korisnika,
- centralizovano rukovanje greškama i povratnim odgovorima.

U praksi, backend predstavlja centralni sloj aplikacije koji povezuje korisnički interfejs, bazu podataka i internu logiku sistema.

---

## 2. Inicijalizacija projekta

Inicijalizacija .NET projekta podrazumeva formiranje osnovne strukture rešenja i definisanje glavnih slojeva aplikacije.

Tipičan tok inicijalizacije izgleda ovako:

1. kreira se **solution** fajl (`.sln`) kao centralna tačka projekta,
2. dodaje se jedan ili više `.csproj` projekata,
3. definiše se glavni **Web API** projekat,
4. po potrebi se izdvajaju dodatni slojevi kao što su:
   - domen/modeli,
   - aplikaciona logika,
   - pristup podacima,
   - testovi,
5. povezuje se baza podataka,
6. registruju se servisi, konfiguracija i middleware komponente,
7. definišu se kontroleri i API rute.

Ukoliko je projekat organizovan kroz slojeve, backend je obično podeljen tako da svaki deo ima jasnu odgovornost, čime se olakšava održavanje, testiranje i dalje proširenje sistema.

## 4. Objašnjenje glavnih delova projekta

### 4.1 Solution fajl (`.sln`)

Solution fajl povezuje sve projekte u jedinstveno rešenje.  
Njegova uloga je da omogući da se backend posmatra kao celina, čak i kada je podeljen na više zasebnih projekata.

Najčešće sadrži reference na:

- glavni API projekat,
- class library projekte,
- test projekte.

---

### 4.2 API sloj

API sloj je ulazna tačka aplikacije. U njemu se obično nalaze:

- `Program.cs`
- kontroleri (`Controllers/`)
- konfiguracija middleware-a
- registracija servisa
- konfiguracioni fajlovi (`appsettings.json`)

Njegove odgovornosti su:

- prihvatanje HTTP zahteva,
- prosleđivanje zahteva odgovarajućim servisima,
- vraćanje odgovora klijentu u odgovarajućem formatu,
- konfiguracija pipeline-a aplikacije.

#### Najvažniji fajl: `Program.cs`

U modernim .NET projektima `Program.cs` je centralno mesto za:

- kreiranje aplikacije,
- registraciju servisa u dependency injection kontejner,
- povezivanje sa bazom,
- aktivaciju autentifikacije/autorizacije,
- mapiranje kontrolera i ruta,
- pokretanje aplikacije.

---

### 4.3 Controllers

Kontroleri predstavljaju HTTP sloj aplikacije.  
U njima se definišu endpoint-i koje frontend ili drugi sistemi pozivaju.

Primer odgovornosti kontrolera:

- prijem zahteva,
- validacija osnovnog formata ulaza,
- pozivanje servisnog sloja,
- slanje odgovarajućeg HTTP statusa i rezultata.

Kontroleri **ne bi trebalo** da sadrže kompleksnu poslovnu logiku. Njihova uloga je da budu tanak sloj između klijenta i ostatka sistema.

---

### 4.4 Domain sloj

Domain sloj sadrži glavne poslovne entitete sistema.

Tu se najčešće nalaze:

- entiteti,
- enumeracije,
- vrednosni objekti,
- osnovna pravila domena.

Ovaj sloj predstavlja srž aplikacije i treba da bude što nezavisniji od tehničkih detalja kao što su baza, HTTP ili spoljne biblioteke.

---

### 4.5 Application sloj

Application sloj sadrži poslovne slučajeve upotrebe sistema.

Ovde se obično nalaze:

- servisi,
- interfejsi,
- DTO objekti,
- komandni i upitni modeli,
- validaciona pravila.

Njegova svrha je da orkestrira rad sistema:

- prima zahtev iz API sloja,
- koristi domenske objekte,
- komunicira sa repozitorijumima ili drugim servisima,
- vraća rezultat kontroleru.

---

### 4.6 Infrastructure / Persistence sloj

Ovaj sloj je zadužen za tehničku implementaciju pristupa podacima i spoljnim resursima.

Tu se tipično nalaze:

- `DbContext`,
- migracije,
- implementacije repozitorijuma,
- konfiguracija entiteta,
- integracije sa spoljnim servisima,
- pomoćne klase za rad sa fajlovima, tokenima, email servisima i slično.

Ako projekat koristi Entity Framework Core, ovde se obično nalaze:

- klase modela za mapiranje,
- `OnModelCreating` konfiguracija,
- migracije baze,
- seed logika za početne podatke.

---

### 4.7 DTO modeli

DTO (Data Transfer Object) služi za razmenu podataka između slojeva i prema klijentu.

Njihova uloga je da:

- ne izlažu interne entitete direktno,
- precizno definišu šta ulazi u sistem,
- precizno definišu šta izlazi iz sistema,
- olakšaju validaciju i verzionisanje API-ja.

Najčešće postoje:

- `Request DTO` modeli,
- `Response DTO` modeli.

---

### 4.8 Konfiguracioni fajlovi

Najčešći konfiguracioni fajlovi su:

- `appsettings.json`
- `appsettings.Development.json`

U njima se obično nalaze:

- connection string-ovi,
- JWT podešavanja,
- log konfiguracija,
- nazivi spoljnjih servisa,
- drugi parametri potrebni aplikaciji.

Ovi fajlovi ne predstavljaju logiku, već centralno mesto za upravljanje konfiguracijom projekta.

## 5. Kako backend projekat funkcioniše

Osnovni tok rada jednog zahteva izgleda ovako:

```text
Klijent (frontend / Postman / drugi servis)
        ↓
HTTP zahtev
        ↓
Controller
        ↓
Service / Application sloj
        ↓
Repository / DbContext / Infrastructure
        ↓
Baza podataka
        ↓
Rezultat nazad ka klijentu
```

### Tok obrade u praksi

1. klijent šalje zahtev na određeni endpoint,
2. kontroler prihvata zahtev,
3. poziva se odgovarajući servis,
4. servis obrađuje logiku i po potrebi pristupa bazi,
5. rezultat se mapira u DTO,
6. API vraća odgovor klijentu.

Ovakva podela omogućava bolju čitljivost, lakše testiranje i jednostavnije buduće izmene.

## 6. Pokretanje projekta

Pokretanje backend projekta podrazumeva da aplikacija bude spremna da prima HTTP zahteve i komunicira sa bazom podataka.

### Standardni način pokretanja

U glavnom API projektu koristi se:

```bash
dotnet run
```

Ako postoji solution sa više projekata, često se backend pokreće iz API projekta, jer je on ulazna tačka aplikacije.

### Alternativno pokretanje preko solution fajla

```bash
dotnet build
dotnet run --project path/to/Api.csproj
```

### Šta se dešava pri pokretanju

Pri pokretanju aplikacije se najčešće izvršava sledeće:

- učitava se konfiguracija,
- registruju se servisi,
- uspostavlja se veza sa bazom,
- aktiviraju se middleware komponente,
- mapiraju se rute kontrolera,
- aplikacija počinje da sluša definisani port.

---

## 7. Povezivanje sa bazom podataka

Backend je najčešće povezan sa bazom preko connection string-a i `DbContext` klase.

### Glavni elementi povezivanja

- connection string u konfiguraciji,
- registracija baze u `Program.cs`,
- `DbContext` klasa,
- migracije i struktura šeme,
- entiteti i relacije.

Tipična registracija baze u .NET aplikaciji izgleda konceptualno ovako:

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.Use...(...));
```

Konkretna baza može biti, na primer:

- PostgreSQL,
- SQL Server,
- SQLite,
- MySQL.

---

## 8. Migracije i stanje baze

Ako projekat koristi Entity Framework Core, migracije predstavljaju verzionisanu istoriju promena šeme baze.

One omogućavaju da:

- struktura baze bude usklađena sa modelima,
- promene budu praćene kroz vreme,
- više članova tima radi nad istom šemom na kontrolisan način.

U okviru projekta je važno razumeti da migracije:

- pripadaju sloju za perzistenciju,
- prate promene modela,
- omogućavaju ažuriranje baze bez ručnog menjanja tabela.

---

## 9. Povezivanje sa frontendom

Frontend se povezuje sa backendom preko HTTP API poziva.

To znači da frontend:

- šalje `GET`, `POST`, `PUT`, `DELETE` zahteve,
- prima JSON odgovore,
- koristi definisane rute backend aplikacije.

### Šta mora biti usklađeno

Da bi povezivanje radilo ispravno, potrebno je da budu usklađeni:

- base URL backend aplikacije,
- port na kom backend sluša,
- tačne rute endpoint-a,
- format request i response objekata,
- CORS pravila, ako frontend i backend rade na različitim adresama ili portovima,
- autentifikacija, ukoliko je projekat zaštićen.

---

## 10. Autentifikacija i autorizacija

Ako backend koristi prijavu korisnika, obično su uključeni sledeći elementi:

- login endpoint,
- generisanje tokena,
- prosleđivanje tokena kroz zaglavlje zahteva,
- zaštita određenih ruta.

Najčešći scenario je JWT autentifikacija:

1. korisnik pošalje kredencijale,
2. backend proverava podatke,
3. backend vraća token,
4. frontend čuva token,
5. naredni zahtevi nose token u `Authorization` header-u,
6. zaštićeni endpoint-i proveravaju validnost tokena.

Na taj način se obezbeđuje da samo autorizovani korisnici imaju pristup određenim resursima.

## 11. Swagger i testiranje endpoint-a

Mnogi .NET backend projekti koriste Swagger/OpenAPI za pregled i testiranje dostupnih ruta.

Swagger omogućava:

- pregled svih endpoint-a na jednom mestu,
- pregled ulaznih i izlaznih modela,
- testiranje zahteva bez posebnog klijenta,
- lakšu komunikaciju između backend i frontend tima.

Ako je uključen u projektu, obično se aktivira pri pokretanju aplikacije i dostupan je kroz posebnu URL adresu.

## 12. Šta je važno pri održavanju projekta

Da bi backend ostao stabilan i pregledan, važno je poštovati sledeća pravila:

- poslovnu logiku ne treba stavljati u kontrolere,
- pristup bazi treba da bude centralizovan,
- modeli za bazu i modeli za API ne treba da budu isto,
- konfiguracija treba da bude izdvojena od logike,
- nove funkcionalnosti treba dodavati u skladu sa postojećom strukturom,
- nazivi foldera, klasa i fajlova treba da budu dosledni.

## 13. Sažetak rada sa projektom

Za praktičan rad sa .NET backend projektom najvažnije je razumeti sledeće:

1. **solution** okuplja sve projekte,
2. **API projekat** je ulazna tačka aplikacije,
3. **kontroleri** izlažu rute,
4. **servisi** sadrže poslovnu logiku,
5. **baza** je povezana kroz konfiguraciju i `DbContext`,
6. **DTO modeli** kontrolišu razmenu podataka,
7. **pokretanje projekta** aktivira kompletan HTTP pipeline,
8. **frontend** komunicira sa backendom preko API poziva.

- lakše razumevanje sistema,
- jednostavnije uvođenje novih funkcionalnosti,
